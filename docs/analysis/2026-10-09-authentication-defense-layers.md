# 消息认证的防线归属与可测影响（P4）

配套规格：`docs/superpowers/specs/2026-10-09-p4-message-authentication-spec.md`

## 1. 结论摘要

1. **四条注入攻击在认证关闭时已各自被不同防线挡下**，认证开启后全部
   归并到最外层的 `BAD_AUTH`。**聚合指标完全不变**——这是可预期的，不是
   认证无效。
2. 认证真正的价值在**它独有的两类情形**：滑动窗口与既有防线**都防不住**
   的「先到的冒充者」与「`msg_id` 预占」。这两类无法用整场景指标体现，
   只能在 `accept()` / `receive()` 层面精确验证（见 §4）。
3. 认证**不防**内部成员伪造，也**不防**重放。这两条边界如实记录。

## 2. 防线归属矩阵

四类攻击，各自单独注入，600 s 基线场景，记录注入消息最终被哪个原因码拒绝：

| 攻击类型 | 认证关闭 | 认证开启 |
|---|---|---|
| `replay`（seq=10⁷） | `SEQ_OUT_OF_WINDOW` | `BAD_AUTH` |
| `stale_epoch` | `STALE_EPOCH` | `BAD_AUTH` |
| `expired` | `DEADLINE_MISSED` | `BAD_AUTH` |
| `forged_join` | `STALE_SESSION` | `BAD_AUTH` |

**读法**：认证关闭时，四条攻击分别由四种不同的机制拦住——序号滑动窗口、
任期检查、有效期检查、会话检查。这四条防线任何一条出问题，对应的攻击就
会穿透。认证开启后，四者都在**最外层**被同一个机制拦下。

这是「纵深」与「单点」的区别：不是"原来防不住、现在防住了"，而是
"原来要依赖四个各自为政的检查同时正确，现在有一个共同的前提"。

## 3. 聚合指标：为什么不改变

| 量 | 认证关闭 | 认证开启 |
|---|---|---|
| 任务完成率 | 1.000 | 1.000 |
| 投递确认成功率 | 0.909 | 0.909 |
| 控制消息丢失率 | 0.0523 | 0.0523 |
| 重传次数 | 0 | 0 |
| 路由切换次数 | 5 | 5 |
| 事件总数 | 56596 | 56596 |

**逐项相同**。原因很直接：每类攻击是**一条消息**，无论被哪一层拦下，
它都只是被丢弃——不消耗带宽、不触发重传、不改变路由、不影响任务。
在 56588 个事件的基线里，4 条消息的去留不可能移动任何聚合量。

**这不应被读成"认证没用"**。它说明的是：**这四类攻击在本场景的规模下
够不上聚合指标的分辨力**。用整场景指标去论证认证的价值是**用错了仪器**
——量不出差异不等于没有差异。

反过来说：如果某次攻击**改变**了聚合指标，那才说明防线真的漏了，因为
单条注入本不该有任何可测影响。

## 4. 认证独有的两类情形（既有防线完全防不住）

这两类**无法**在整场景里稳定复现，因为残差的前提是「接收端从未见过该
流」或「攻击者抢在真实消息之前」——在整场景里时序难以稳定构造。它们在
`accept()` / `receive()` 层面精确验证。

### 4.1 先到的冒充者

接收端从未见过某条 `(src, msg_type)` 流时**没有基准**，冒充者那个 10⁷
会被当作锚点收下，此后真实节点的正常序号全部落在窗口**后面**被判
`STALE_SEQ`——单封包就能让一个真实节点从视野里消失。

实测（`tests/unit/test_auth.py::TestFirstArrivingSpoofer`）：

```
认证关闭：冒充者 seq=10^7 -> ACCEPT ；真实 seq=1 -> STALE_SEQ   ← 被打瞎
认证开启：冒充者 seq=10^7 -> BAD_AUTH；真实 seq=1 -> ACCEPT     ← 关闭
```

### 4.2 `msg_id` 预占（实现 P4 时被探针发现的缺陷）

`new_msg_id()` 返回 `f"{node_id}:{n}"`，`n` 是每节点从 1 递增的计数器，
**完全可预测**。`DedupTable.seen()` 又是「检查时即登记」。初版把认证放在
`accept()` 内部，而 `receive()` 的去重检查在它**之前**——于是未认证的
消息在被拒绝前就已经登记了 `msg_id`，随后真实消息被判 `DEDUP` 丢弃。
**认证开着也挡不住**，因为认证根本还没跑。

实测（`tests/integration/test_message_authentication.py::
TestNoStateMutationBeforeAuthentication`）：

```
修复前：认证开启，预占伪造 -> BAD_AUTH（被拒）；真实消息 -> DEDUP（被误杀）
修复后：认证开启，预占伪造 -> BAD_AUTH（被拒）；真实消息 -> ACCEPT
```

根因：「未经认证的消息，其所有字段都不可信」里的"所有字段"**包括
`msg_id`**。初版只想到 `leader_epoch` 这类协议字段，而 `msg_id` 恰恰是
唯一一个在认证之前就被写进状态的字段。

## 5. 认证**不**覆盖的边界

| 不防 | 由谁负责 / 为何不防 |
|---|---|
| **重放**（抓到的真实消息，MAC 有效） | 序号窗口 + 去重表。认证若把重放也算成伪造，序号窗口的意义就被架空了——两套机制各司其职 |
| **内部成员伪造** | 组密钥的固有边界：持有密钥即可签名。选组密钥而非非对称签名是有代价的取舍（场景是同一集群内网），代价必须被记录 |
| **成员管理**（谁能拿到密钥） | 本仿真范围之外。4.2 的教训说明这类"前提性"缺口容易被漏看 |

第三条值得强调：认证解决的是「消息是否来自声称的发送者」，**不解决**
「声称的发送者是否应当持有密钥」。后者需要密钥分发与吊销机制，本仿真
不涉及——但不应因此以为"开了认证就安全了"。
