## 1. 文档定位

`计网报告.docx` 是一份**需求分析**，它规定了"要什么"但没有"怎么做"。本方案把报告中散落在
表格 2-1 ~ 2-4、表 3-1、表 4-1、表 4-2 以及"实验记录与评价边界"一节的要求，收敛为一份
**可实现的仿真设计**。

设计目标不是堆功能，而是让报告中每一句可验证的命题，都能在仿真里找到**对应的字段、事件或指标**。
凡报告中无法落到字段的表述，本方案要么给出落地方式，要么列入第 14 节开放问题。

### 1.1 基线场景（P0）

| 项目 | 取值 |
|---|---|
| 节点规模 | 1 主节点 + 8 从节点 + 2 中继 = 11 |
| 空间范围 | 500 m × 500 m |
| 建筑模型 | 规则网格楼群（矩形底面 + 高度，楼高 50 ~ 110 m） |
| 巡航高度 | 140 m（高于全部楼顶），转场时使用 |
| 投递高度 | 80 ~ 110 m（街道峡谷内），取餐点/投递点使用 |
| 任务数 | 20 个配送任务 |
| 仿真时长 | 单次实验 600 s 虚拟时间 |

**任务剖面**：无人机在巡航高度转场，到取餐点/投递点下降进入峡谷，
投递完成后**爬升脱离遮挡再上报**投递确认。遮挡因此是每次投递都会
短暂发生、并可自动恢复的现象，而不是"整段航程全遮挡"或"完全无遮挡"
的二值结果（理由与实测数据详见 §15.9、§15.11）。

选择小场景的理由：先把机制与指标跑稳、跑可复现，再放大规模。规模放大属于 P1。
压力对照场景见 `scenarios/stress_canyon.json`（§15.11）。

## 3. 架构总览

```
┌──────────────────────────────────────────────────────────┐
│  L4 观测层 observe/  （横切，被各层写入，不依赖任何层）      │
│     事件日志 JSONL → 九项指标 → 时间线回放                  │
├──────────────────────────────────────────────────────────┤
│  L3 业务层 mission/                                       │
│     任务生命周期 · 投递确认与幂等 · 失败重派 · 本地安全动作   │
├──────────────────────────────────────────────────────────┤
│  L2 协议层 protocol/                                      │
│     身份/会话/角色 · 成员状态机 · 版本与去重 · 消息格式       │
│     Q0-Q4 队列 · R0-R3 可靠性 · 基础通信关系与 route_version │
├──────────────────────────────────────────────────────────┤
│  L1 世界层 world/                                         │
│     几何 · 楼块 · 节点运动 · 链路模型(可插拔) · 共享信道      │
├──────────────────────────────────────────────────────────┤
│  L0 仿真核心 kernel/                                      │
│     虚拟时钟 · 事件优先队列 · 调度器 · 独立随机源 · 配置       │
└──────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：L3 → L2 → L1 → L0。L4 被所有层写入，但不被任何层依赖
（指标计算只读日志，不回写仿真状态）。这条约束保证：指标定义可以改而无需重跑仿真，
P1 可以替换链路模型而不触碰协议层。

**为何不引入 ROS 2 / ns-3 / simpy**：报告 §1 明确排除"完整飞控、真实飞行动力学、
城市空域审批"，因此不需要机器人中间件与物理引擎；报告要求的 session_id、leader_epoch、
mission_version、operation_id 去重全部属于**应用层**逻辑，在 ns-3 中需以 C++ 编写应用层，
投入产出比不划算。P0 使用**纯标准库 Python**，零第三方依赖。

## 4. L0 仿真核心 kernel/

### 4.1 时间与事件模型

- 单一全局虚拟时钟 `t`（float，单位秒），无实时映射。
- 事件定义为 `(t, tie, kind, payload)`；优先队列以 `(t, tie)` 排序，`tie` 为单调递增
  序号。**引入 `tie` 是为了让同一时刻的事件有确定顺序**，否则堆的内部顺序会造成两次运行
  结果不一致。
- 事件循环：弹出最早事件 → 推进时钟 → 交付给该事件的处理器 → 处理器可注册新事件。
- 不使用多线程、不使用真实睡眠。仿真为完全确定性单线程。

### 4.2 独立随机源（关键决定）

**不使用同一个全局随机流。** 每个随机来源持有独立 `random.Random` 实例，其种子由
`(master_seed, stream_name)` 派生：

```python
def stream(master_seed: int, name: str) -> random.Random:
    h = hashlib.blake2b(f"{master_seed}:{name}".encode(), digest_size=8).digest()
    return random.Random(int.from_bytes(h, "big"))
```

命名约定：`node:<id>:mobility`、`node:<id>:heartbeat`、`channel:collision`、
`env:occlusion_jitter`。

理由：若所有随机数出自同一条流，则"增加一个节点"会使后续所有抽样整体位移，
导致任何 A/B 对比（例如改一个门限参数）失去意义。独立流使每个来源可单独复现。

**实现警告**：派生种子必须使用 `hashlib`，不可使用 Python 内建 `hash()`——
字符串 `hash()` 受 `PYTHONHASHSEED` 影响，逐进程变化，会直接破坏可复现性。

### 4.3 事件与原因码

`observe/events.py` 定义封闭枚举（新增必须改枚举，防止日志出现自由文本）：

**事件类型**：`NODE_JOIN`、`NODE_LEAVE`、`NODE_REJOIN`、`ROLE_CHANGE`、`STATUS_CHANGE`、
`HEARTBEAT_TX`、`HEARTBEAT_MISS`、`MSG_TX`、`MSG_RX`、`MSG_FORWARD`、`MSG_DROP`、
`MSG_DUP`、`MSG_EXPIRE`、`CHANNEL_BUSY`、`OCCLUSION_ENTER`、`OCCLUSION_EXIT`、
`TASK_CREATE`、`TASK_ASSIGN`、`TASK_PICKUP`、`TASK_DELIVER`、`TASK_FAIL`、`TASK_REASSIGN`、
`SAFETY_ACTION`、`QUEUE_SAMPLE`、`ENERGY_SAMPLE`。

**丢弃原因码**（报告要求"丢弃、重复和过期**原因**"）：

| 原因码 | 含义 |
|---|---|
| `OCCLUDED` | 几何遮挡导致链路不可用 |
| `COLLISION` | 共享信道竞争冲突 |
| `QUEUE_FULL` | 本地发送队列溢出 |
| `TTL_EXPIRED` | 跳数或生存时间耗尽 |
| `DEADLINE_MISSED` | 超过消息有效期，已无重传价值 |
| `DEDUP` | operation_id 命中去重表 |
| `STALE_EPOCH` | 来自旧任期的消息 |
| `STALE_SESSION` | 来自旧会话（重连前）的消息 |
| `STALE_VERSION` | 旧 mission_version / route_version |
| `NO_ROUTE` | 当前通信关系不可达 |
| `RATE_LIMITED` | 高优先级配额耗尽（防异常节点灌爆） |
| `UNAUTHORIZED` | 权限校验失败（P1 注入用） |

### 4.4 配置

场景与参数由一份 JSON 配置驱动（`scenarios/baseline_small.json`），命令行可覆盖单项
（`--seed`、`--duration`、`--nodes`）。**所有门限参数必须出现在配置里，不得硬编码**——
第 6.2 节的状态机门限与第 8.4 节的阈值标定都依赖这一点。

## 5. L1 世界层 world/

### 5.1 几何

`geometry.py` 提供点、线段、矩形、线段-矩形相交判定、欧氏距离。纯函数，无状态，
是单元测试覆盖的重点（遮挡判定的正确性完全依赖它）。

### 5.2 楼块

`Building` = 矩形底面（x, y, w, h）+ 高度 `height`。基线场景由配置生成规则网格。

### 5.3 节点与运动

- `Node` 静态属性：`node_id`（长期身份，不变）、`role`、能力声明。
- `Node` 运动状态：位置 `(x, y, z)`、速度、航向、剩余能量。
- **能量是被建模的一等状态**，因为报告要求"能耗趋势"指标，且要求区分
  "节点在线"与"节点可用"（低电量节点仍在线但不适合转发/配送）。
- 运动模型：航点式（取餐点 → 投递点），匀速 + 转向，简化避障。**不含飞行动力学**
  （报告明文排除）。

### 5.4 链路模型接口（P1 的保险栓）

```python
class LinkModel(Protocol):
    def evaluate(self, a: Node, b: Node, t: float) -> LinkQuality:
        """返回 (quality: float in [0,1], obstructed: bool, blocked_by: Building | None)"""
```

- **P0 实现** `GeometricOcclusionLinkModel`：若 a-b 连线与任一 `height >= min(a.z, b.z)`
  的楼块相交 → 判定遮挡，`quality` 大幅下降；否则 `quality` 随距离衰减。
- **P1 插槽** `NlosMultipathLinkModel`：绕射衰减 + 多径快衰落 + 与高度相关的抖动。
  只需实现同一接口即可替换，协议层零改动。

`LinkQuality` 含 `quality`、`obstructed`、以及**趋势量** `quality_trend`（滑动窗口斜率），
供第 6.2 节区分"临时遮挡"与"持续失联"。

### 5.5 共享信道（区别于固定丢包率）

报告 §3.1 明确否定固定丢包率。因此信道必须建模为**共享资源**：

- 一次传输占用信道 `tx_duration = size_bits / rate`（默认 rate = 2 Mbps）。
- 信道按时隙划分竞争单位（默认 2 ms）。落在**同一时隙**且发送方互为干扰
  范围（默认 300 m）内的并发发送，双方判定 `COLLISION`。
- 发送等待到下一个时隙边界，这段等待即为 `t_access`。这是"接入时延"与
  "信道竞争"的唯一来源，也是报告所说"投递点附近节点聚集加剧信道竞争"的落点。
- 广播是一次信道占用、多个接收端；每个接收端**各自**判定链路质量与成败。
- 传播时延按光速计算：500 m 约 1.67 μs，相对排队与重传可忽略，但仍记录在
  `t_prop` 字段中，以便答辩时说明已考虑而非遗漏。

> **为什么必须时隙化**（实现阶段修正，详见 §15.1）：若只在"完全相同的浮点
> 时刻"判定冲突，两个独立随机时刻相等的概率为零，冲突数实测**恰好为 0**，
> 报告要求的"信道竞争"这一整块分析会退化为一句"没有冲突"。时隙把连续
> 时间离散成竞争单位，冲突才成为可观测、可统计、可归因的现象。
> 相应地，周期发送须叠加时钟漂移（§15.5），否则各节点的发送时刻是固定
> 相位的排班表，同隙并发同样不会自然发生。

## 6. L2 协议层 protocol/

### 6.1 身份、会话与角色

| 字段 | 性质 | 说明 |
|---|---|---|
| `node_id` | 长期、不变 | 不随网络地址/接入方式变化 |
| `session_id` | 每次加入新生成 | `f"{node_id}#{join_counter}"`，用于区分重连前后 |
| `role` | 动态 | `LEADER` / `SLAVE` / `RELAY` / `STANDBY` |
| `lease` | 有有效期 | `(node_id, role, epoch, scope, expire_at)` |

规则：
- 收到 `STALE_SESSION` 的消息一律丢弃（重连前的旧消息不得影响当前状态）。
- 节点退出或租约到期 → 相关权限**自动失效**，不需显式撤销消息。
- 加入流程：身份验证 → 能力声明 → 主节点任期确认 → 会话建立。

P0 的"身份验证"为占位实现（接口存在、恒真或简单共享密钥），密码学强度属 P1，
但**权限失效与去重的语义必须是完整的**。

### 6.2 成员状态机（带迟滞）

状态（6 个，对应报告 §2.2.1）：

```
ONLINE ⇄ DEGRADED → SUSPECT → FAILED
   ↑                    │
   └──── REJOINING ─────┘        LEFT（主动退出）
```

三路证据源（报告要求"结合直接心跳、邻居或中继的间接探测、链路质量趋势"）：

1. **直接心跳**：`last_seen`、`heartbeat_seq`、连续丢失计数 `miss_count`
2. **间接探测**：邻居在心跳或成员摘要中报告"曾见到该节点" → 抑制 SUSPECT 判定
3. **链路质量趋势**：`link_quality` 与其斜率

转移规则：

| 从 | 到 | 条件 |
|---|---|---|
| ONLINE | DEGRADED | `miss_count >= N_degraded` **或** `link_quality < Q_degraded` |
| DEGRADED | ONLINE | 收到有效心跳且 `miss_count` 归零 |
| DEGRADED | SUSPECT | `miss_count >= N_suspect` **且** 无间接探测佐证 |
| SUSPECT | DEGRADED / ONLINE | 收到直接心跳，或收到间接探测证据 |
| SUSPECT | FAILED | 持续 `>= T_fail` 秒仍无任何直接或间接证据 |
| 任意 | LEFT | 收到主动退出消息，或租约到期 |
| FAILED / LEFT | REJOINING | 收到携带**新 session_id** 的加入请求 |
| REJOINING | ONLINE | 加入流程完成 |

**门限参数**（全部进配置，供 P1 标定）：`N_degraded=2`、`N_suspect=4`、
`T_fail=3.0 s`、`Q_degraded=0.4`（初值，待标定）。

> 这条设计直接兑现报告那句"不能把单次丢包直接等同于无人机故障"：
> 单次丢包走 `ONLINE → DEGRADED`，只有连续丢失**且**邻居也不作证**且**持续超过
> `T_fail` 才判 FAILED。由于门限可调，报告中的命题变成可扫参数画曲线的实验，
> 而不是一句声明。

**间接探测的意义**：城市遮挡常造成"主节点 → 从节点"直连丢失，但从节点之间仍然可达。
若无间接探测，会把一次遮挡误判为节点故障并触发无谓的任务重派。

### 6.3 版本、任期与顺序（纯函数，优先 TDD）

| 字段 | 作用 | 解决的问题 |
|---|---|---|
| `leader_epoch` | 主节点任期 | 拒绝旧主节点恢复后发出的命令 |
| `mission_version` | 任务方案 | 识别任务更新与过期任务 |
| `route_version` | 通信关系 | 识别旧路由 |
| `seq` | 同版本内先后 | 乱序、重复、丢失 |
| `operation_id` | 一次具体操作 | 重复到达时动作只执行一次 |

接受规则（`version.py`，无副作用纯函数）：

```
accept(msg, local_view) -> Accept | Reject(reason)
  1. msg.leader_epoch < local.leader_epoch            → STALE_EPOCH
  2. msg.session_id 不在有效会话集合                   → STALE_SESSION
  3. msg.mission_version < local.mission_version       → STALE_VERSION
  4. operation_id ∈ dedup_table                        → DEDUP
  5. 同 (src, epoch, version) 且 msg.seq <= local.seq  → （丢弃，静默）
  6. 否则接受，更新 local.seq，登记 operation_id（带 TTL 过期）
```

去重表必须带 TTL 与容量上限，否则长时间仿真会无界增长。

### 6.4 消息格式

```python
@dataclass(frozen=True)
class Msg:
    msg_id: str
    src: str; dst: str
    session_id: str
    leader_epoch: int
    mission_version: int
    route_version: int
    seq: int
    operation_id: str | None
    qos: Qos            # Q0..Q4
    reliability: Rel    # R0..R3
    t_created: float
    deadline: float     # 有效期
    hop: int
    ttl: int
    payload: dict
    checksum: str       # P0 为占位，P1 接管完整性
```

报告 §2.2.4 要求的字段全部在上表中有对应，无遗漏。

### 6.5 可靠性策略（表 2-3 落地）

| 等级 | 典型消息 | 机制 |
|---|---|---|
| R0 | 普通遥测、稳定状态 | 不重传；最新值覆盖旧值（同源同类型只留最新） |
| R1 | 成员状态、邻居与路由关系 | 有限次重传（默认 2）；保留版本信息 |
| R2 | 任务、动作结果、投递确认 | ACK + 超时重传 + 去重 + 过期检查 |
| R3 | 紧急控制、避障、主节点切换 | 高优先级 + 重复发送 + 备用路径；**截止期后不再重传** |

关键点：R2/R3 在 `t > deadline` 后停止重传并记 `DEADLINE_MISSED`——这正是报告
表 4-1 中"可靠重传与信息时效"矛盾的落点：**重传不是无条件的**。

### 6.6 队列与限流

优先级等级沿用报告 §2.2.5 的定义：Q0 紧急控制与避障、Q1 主节点切换/任务/投递确认、
Q2 成员与通信关系、Q3 普通遥测与位置状态、Q4 大数据业务。

- 每个节点 5 条队（Q0–Q4），**严格优先级**调度：高优先级先出队。
- 严格优先级的已知风险是低优先级饿死。因此：
  - 对 Q0/Q1 设 **token bucket 速率上限**（报告明文要求"防止异常节点连续发送紧急消息
    占满城市无线信道"）；超限记 `RATE_LIMITED`。
  - 对 Q3 普通遥测设**最小间隔 + 自适应降频**：链路拥塞或状态稳定时降频；速度/位置
    快速变化时优先发送核心字段（报告 §2.2.5 明文要求）。
- 队列深度上限触发 `QUEUE_FULL`。队列长度随时间采样并写入 `QUEUE_SAMPLE`。

### 6.7 基础通信关系与路由迟滞

- 主节点维护 `route_version`，变更时递增并广播（R1）。
- **迟滞规则**（报告 §3.2 要求"不能因为一次探测结果变化就立即切换路径"）：
  切换需同时满足 `link_quality` 改善超过 `H_up` **且**持续 `T_hold` 秒，
  或当前链路低于 `H_down` 且持续 `T_hold` 秒。
- 记录 `route_version` 递增次数与"短窗口内切回"次数（路由震荡指标）。

## 7. L3 业务层 mission/

### 7.1 任务生命周期

`任务状态`：`CREATED → ASSIGNED → ENROUTE → PICKED → DELIVERED`，
旁支 `FAILED`、`EXPIRED`、`REASSIGNED`。

任务携带 `task_id`（即 `operation_id`）、取餐点、投递点、截止时间、优先级。

### 7.2 投递确认与幂等

- 投递确认属 R2：ACK + 超时重传 + 去重。
- **幂等保证**：以 `operation_id` 为键，重复到达只执行一次动作，第二次记 `DEDUP`。
  这既满足报告"保证重复到达时动作只执行一次"，也为 P1 的重放攻击测试提供对照。

### 7.3 失败重派与任务接管

节点进入 FAILED，或其任务 `deadline` 逼近而进度不足 → 主节点重新指派。
重派需递增 `mission_version`，使在途的旧指派消息自然失效（`STALE_VERSION`）。

### 7.4 本地安全动作

触发条件与动作（**本地自主，不依赖主节点**，报告 §2.2.6 要求）：

| 触发 | 动作 |
|---|---|
| 与主节点及所有中继失联 | `HOVER` 或 `RETURN` |
| 低电量 | `RETURN` 或 `DESCEND` |
| 位置过期（GNSS 退化）或位置误差超限 | `HOVER` + 依赖邻居相对位置避障 |
| 即将进入禁飞区（P1 注入） | `HOLD` |

安全动作产生 `SAFETY_ACTION` 事件，进入事件链以便复盘。

## 8. L4 观测层 observe/

### 8.1 事件溯源日志

- 格式：**JSONL**，一行一事件，append-only。
- 每条含公共字段：`t`、`event_kind`、`node_id`、`session_id`、`leader_epoch`、
  `mission_version`、`route_version`、`msg_id`、`reason`，以及各事件类型特有字段。
- 日志是**唯一事实来源**：仿真过程不直接累计指标。

### 8.2 指标从日志重算

`metrics.py` 只读日志文件，不依赖仿真运行时状态。收益：

1. 指标定义演进时无需重跑仿真；
2. 回放与指标计算共用同一份数据，不会出现两套口径；
3. 便于人工抽查某条消息的完整链路。

### 8.3 时延六段分解

报告 §2.2.5 定义端到端时延由六部分构成。每条消息记录六个分量：

| 分量 | 含义 |
|---|---|
| `t_sample_wait` | 状态变化到进入待发队列（周期采样等待） |
| `t_queue` | 本地优先级队列排队 |
| `t_access` | 信道竞争与接入等待 |
| `t_tx` | 实际传输 `size_bits / rate` |
| `t_forward` | 多跳转发在中间节点的累计（排队 + 接入 + 传输） |
| `t_proc` | 接收端处理（成员表更新、去重、路由决策） |

`E2E = t_sample_wait + t_queue + t_access + t_tx + t_forward + t_proc + t_prop`。

由于六段分别记录，"低时延需求"在报告中从一句论断变成**可归因的诊断**：
时延升高时能直接指出是排队、接入还是转发造成的。

### 8.4 指标定义

报告 §6 说明"阈值待定"，但**定义必须先明确**，否则实验无法复现。

| # | 指标 | 定义 |
|---|---|---|
| 1 | 任务完成率 | `count(TASK_DELIVER) / count(TASK_CREATE)` |
| 2 | 投递确认成功率 | 收到 ACK 的投递确认数 / 发出的投递确认数 |
| 3 | 关键消息 E2E 时延 | R2/R3 消息 `t_rx − t_created`，**按 QoS 与 R 等级分组** |
| 4 | 尾部时延 | 同 #3，取 P50 / P95 / P99 |
| 5 | 控制消息丢失率 | Q0/Q1 的 `MSG_DROP` 数 / 发送数，**按原因码分组** |
| 6 | 重传次数 | 每条消息重传计数之和；另报均值与最大值 |
| 7 | 故障恢复时间 | 节点进入 FAILED 到恢复 ONLINE，或任务被接管的时间 |
| 8 | 路由切换次数 | `route_version` 递增次数；另报短窗口回切次数（震荡） |
| 9 | 单位任务通信开销 | 总字节数 / 完成任务数；**分控制面与业务面** |
| 10 | 能耗趋势 | 每节点能量消耗时间序列（发送 + 转发 + 悬停加权） |

> 计数口径说明：报告列举九项，其中"关键消息端到端时延及其尾部时延"为一整项。
> 本方案将其拆为上表 #3 与 #4 两行，以便分别报告，故表中共十行。
> 二者必须分开——均值会被大量 Q3 遥测淹没，而报告真正关心的是 R3 紧急控制的尾部行为。
> 对外的指标汇总仍按报告的九项呈现（见 §14.2 开放问题 1）。

### 8.5 回放与确定性验证

- **回放**：读 JSONL 重建时间线（节点状态、消息流转、任务进度），无需重跑仿真。
- **确定性验收测试**：相同 `master_seed` 连续运行两次，日志规范化后 SHA-256 必须一致。
  这是本设计的头号回归测试——一旦被打破，所有 A/B 对比与结论都失去意义。

## 11. 测试策略

**单元测试（TDD，先红后绿）**——优先覆盖纯函数，性价比最高：

- `version.accept()` 的六条规则逐条断言，含边界（同 epoch 同 seq、去重表 TTL 过期）

**集成测试**——完整事件链断言：

**确定性测试**：同 seed 两次运行，日志 SHA-256 一致。

**场景测试**：基线场景（11 节点 / 20 任务 / 600 s）跑通，输出全部指标。

## 12. 关键设计决策与理由

| # | 决策 | 理由 |
|---|---|---|
| 1 | 自建 DES，不用 simpy / ns-3 | 零依赖、可解释、时延六段分解天然对应事件边界 |
| 2 | 共享信道资源，而非每链路固定丢包率 | 报告 §3.1 明确否定固定丢包率，且"信道竞争/队列"无处产生 |

| 4 | 每个随机来源独立 RNG 流 | 保证 A/B 对比有效（否则增删节点会位移全部随机序列） |
| 5 | 指标从日志重算 | 指标定义可演进，回放与指标共用一份事实来源 |
| 6 | 成员状态机迟滞门限全部参数化 | 把报告"不能把单次丢包等同故障"变成可扫参数的实验 |
| 7 | 重传受 `deadline` 约束 | 兑现表 4-1"可靠重传与信息时效"矛盾 |
| 8 | 幂等以 `operation_id` 为键 | 兑现"重复到达时动作只执行一次"，并为 P1 重放测试留对照 |
| 9 | 事件时间戳加单调 `tie` | 消除同刻事件顺序的不确定性 |
| 10 | P0 只做通信，不含飞控与动力学 | 报告 §1 明文范围界定 |

## 15. 实现阶段的设计修正（2026-10-04 记录）

实现与验收过程中，以下设计点被证明**原方案是错的**，此处逐条记录修正与理由。
每一条都不是调参，而是模型/协议层面的缺陷；判据是"它会让报告要求的某个
可观测现象消失或失真"。

### 15.1 信道必须是**时隙化**竞争，否则冲突恒等于 0

原方案：只在"同一虚拟时刻"结算冲突。但仿真时刻是浮点数，两个独立随机
时刻相等的概率为零，实测冲突数**恰好为 0**——报告 §5.5 要求的"信道竞争"
这一整块分析会退化成一句"没有冲突"。

修正：信道按时隙（默认 2 ms）划分竞争单位，落在同一时隙且互相处于干扰
范围内的并发发送判为冲突。发送等待到**下一个**时隙边界，这段等待就是
接入时延。

因果性约束：时隙号向上取整。若把发送时刻回退到当前时隙起点，在时隙末尾
产生的消息会"在产生之前"发出去，端到端时延算出负值、虚拟时钟倒退。

### 15.2 完全遮挡的发送必须**记入日志**

原实现在链路质量为 0 时直接返回、不登记发送尝试，于是"整个链路被楼挡住"
的丢包在日志里**完全不存在**。修正后同一场景的遮挡丢包从 143 变为 4228。
日志不完整会让"遮挡导致劣化"的结论建立在错误的基数上。

### 15.3 广播是**一次发送**，不是 N 次单播

原实现把主节点心跳按成员逐个单播。后果有两层：空口负载凭空放大 N 倍，
冲突率被自己推高；指标里 1 次广播对应 N 次接收，送达率算出 180%。

修正：广播记为一次信道占用，接收端逐个判定链路质量；指标侧统一按
"发送 × 接收端"配对计数（分母乘 N-1）。广播**不得转发**——否则每个收到
它的节点都会转发一次，转发量等于节点数乘广播速率。

### 15.4 中继是补线，不是优选；而且是**基础设施**

两处错误：
1. 只要中继链路比直连好 0.05 就切过去，使每次心跳都多占一跳空口时间，
   负载翻倍。修正为**仅当直连质量低于门限**（默认 0.6）才把中继列为候选。
2. 中继被派发配送任务后飞离站位、进入低空，既不再提供覆盖，又成为最易
   被遮挡的节点。修正为**中继不参与任务分配**。
3. 中继必须放在内圈高空。与从节点同圈同高度时，两者看到的遮挡几乎一样，
   中继对任何链路都不会更好——转发路径形同虚设。

另外，中继自身不参与上游选择：R1 选 R2、R2 选 R1 会形成转发环路，
消息只能在 TTL 耗尽后消失，看起来像丢包，实际是路由环路。

### 15.5 周期发送必须带**时钟漂移**

原实现各节点的发送时刻是严格周期加固定初始相位，彼此几乎永不重叠。
除 §15.1 的时隙外，还须叠加每次发送的漂移（默认 ±50 ms），使到达过程
接近随机的竞争，而不是一个精确的排班表。相应地，失联判定阈值从
1.0 个周期放宽到 1.5 个周期，否则正常漂移会被误判为丢包。

### 15.6 协议层三处修正

1. **版本检查只作用于任务域消息**。心跳、遥测等状态消息带
   `mission_version` 毫无意义，却会因任务重派而被判 `STALE_VERSION`。
   现仅对 `TASK_ASSIGN/TASK_REASSIGN/DELIVERY_CONFIRM` 生效。
2. **序号按消息流分别记账**。心跳与遥测共用一个序号计数器时，
   一条乱序遥测会让随后的心跳被判 `STALE_SEQ`（实测 129 次误判）。
   现 `last_seq` 的键为 `(src, msg_type, leader_epoch, mission_version)`。
3. **重传副本也要回 ACK**。去重抑制的是"动作"，不是"确认"。原实现
   在去重分支直接返回，源端会一直重传到有效期结束，而接收端其实早已
   处理过。现对 `DEDUP` 与 `STALE_SEQ` 两种情况补发确认。

### 15.7 周期消息不盲目重传

心跳是 R1（尽力而为）。把 R1 也纳入重传，会让周期性消息的重传副本
淹没信道（实测 619 次误判 `STALE_SEQ`）。现仅 `>= R2` 登记重传。

### 15.8 任务闭环止于确认被 ACK

1. 发送投递确认后**停在原地等 ACK**，而不是发完即算完成。否则一次确认
   丢失就会让任务永远停在"已取件"：节点飞走了、任务没交付、主节点也不知道。
2. 投递确认的有效期由业务决定（5 s），不沿用 R2 的默认 1 s。
3. ACK 处理器必须按**接收节点**绑定。ACK 的 `src` 是主节点，而"谁在等这个
   ACK"只有接收方知道；用 `src` 查等待表永远查不到，节点会永远停在投递点，
   任务完成率被死死钉在"每节点恰好一个"（实测 10/20 无法再提高）。

### 15.9 航线 = 高空巡航 + 末端下降 + 爬升后上报

若让无人机一路低空穿越城区，链路会被**长时间**遮挡，看起来像网络分区，
观察到的不是"遮挡导致的劣化"而是"网络不存在"。

修正为三段航线：升到巡航高度转场 → 下降到投递点 → **爬升脱离峡谷后再上报**。
低空链路上确认发不出去、ACK 也回不来，停在原地等只会卡死到有效期结束；
投递动作本身早已完成，却因上报路径不可用而被判失败。真实低空配送系统
同样是"投递后爬升再回传"。

配套要求：`WaypointMover` 只有**整条航线走完**才算抵达。若把"到达任意一个
航点"当作抵达，无人机会在巡航高度上直接开始投递，永远不下降。

### 15.10 指标口径修正

1. **丢失率 = 丢弃 / 尝试**。用成功次数作分母，在链路很差时会算出
   156% 的"丢失率"——那不是指标，是口径错误。
2. **心跳送达率**按"发送 × 接收端"配对计（见 §15.3）。
3. **六段时延分解**中，采样等待与排队只对本机产生的消息有意义。
   广播接收方与转发副本的接收方从未在本机排队，须记 0，
   不能拿 0.0 去减生成时刻（实测图中出现 -30 万毫秒）。

### 15.11 基线与压力场景分离

几何参数下遮挡呈**二值**：要么几乎全遮挡、要么完全不遮挡，中间地带极窄
（源于航点高度的离散取值）。因此改为三个受控场景，而不是试图把一个场景
"调"到中间。三者共用同一套协议，只改环境与负载：

| 场景 | 文件 | 特征 | 任务完成 | 控制丢包 | 心跳送达 |
|---|---|---|---|---|---|
| 基线 | `scenarios/baseline_small.json` | 500 m、8 从、2 中继、20 任务 | 20/20 | 5.2 % | 99.5 % |
| 压力 | `scenarios/stress_canyon.json` | 城区 700 m、遥测 4 Hz、投递高度 50–90 m | 2/20 | 35.4 % | 48.4 % |
| 故障 | `scenarios/fault_chain.json` | 基线 + S2 于 60 s 静默、120 s 恢复；R1 于 150 s 静默 | 9/12 | 14.5 % | 84.4 % |

对照本身即结论：同样的协议，在遮挡与负载变化下从可用跌到近乎不可用。
故障场景则给出报告 R0–R3 要求的完整链路实测时间线（S2：62 s DEGRADED、
64 s SUSPECT、67 s FAILED、120 s 重新入网、120.85 s ONLINE），
并由 `tests/integration/test_fault_scenario.py` 断言升级顺序与阈值一致性。

### 15.12 CLI 产物必须按场景命名

原实现把日志与报告名硬编码为 `baseline`。三个场景依次运行时互相覆盖，
读 `out/logs/baseline.jsonl` 拿到的是最后一次运行的结果——一个会让人
得出完全错误结论的缺陷。现按场景名分目录：`out/logs/<name>.jsonl`、
`out/figures/<name>/`、`out/replay/<name>.html`。
