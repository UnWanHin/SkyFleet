# P4 规格：消息认证（关闭「先到的冒充者」残差）

对标：`docs/superpowers/specs/2026-10-06-p2-protocol-gaps-spec.md` §1.4b
记录的**已知残差**——无认证时，序号滑动窗口防不住「先到的冒充者」。

## 1. 残差是什么

P2 切片 A 的滑动窗口解决的是「基准已存在」的情形：被冒充的节点一直在
发消息，接收端有 `last_seq` 可比，冒充者那个 10^7 的大序号会越窗被拒。

但若接收端**从未见过**该 `(src, msg_type)` 流，就没有基准：10^7 会被
当作锚点收下，此后真实节点的正常序号反而全部落在窗口**后面**被判
`STALE_SEQ`。消息结构里的 `checksum` 至今是 P0 占位（恒为空串）。

**这不是滑动窗口的参数问题，是「无认证」的本质边界。** 任何基于序号、
会话、任期的检查都建立在「消息确实来自它声称的发送者」之上；没有认证，
这个前提不成立。要真正关掉它，只能引入认证。

## 2. 设计：MAC 而非签名

选 **HMAC-SHA256 + 全网预共享密钥**，截断到 128 位。

| 选项 | 取舍 |
|---|---|
| 非对称签名（Ed25519 等） | 更贴近"公钥基础设施"，但引入密钥分发与实现的复杂性，而本项目的场景是**同一集群的内网**，预共享组密钥是现实做法 |
| **HMAC + 组密钥**（选它） | 与真实集群通信（如 MAVLink 2 的签名、组播组密钥）一致；纯标准库 `hmac`+`hashlib` 即可，无新依赖 |
| 不认证 | 残差留着 |

**明确不防的**：内部成员持有组密钥，因此「被攻陷的成员」可以伪造。
这是组密钥方案的固有边界，**如实记录**，不假装认证解决了一切。

### 2.1 MAC 覆盖哪些字段

覆盖**内容与来源**，**排除**转发时会变的字段：

| 覆盖 | 排除（及理由） |
|---|---|
| `msg_id`、`msg_type`、`src`、`dst` | `hop`、`ttl`：中继转发时必然改变（`replace(msg, hop=..., ttl=...)`），纳入会让每一跳都验签失败 |
| `session_id`、`leader_epoch`、`mission_version`、`route_version` | `deadline`、`qos`、`reliability`：由 `Msg.new` 按类型推导，非独立信息 |
| `seq`、`operation_id`、`t_created`、`payload` | `checksum` 本身 |

`src` **必须**在覆盖范围内——否则冒充者可以换掉 `src` 而 MAC 依然有效，
那就完全没防住冒充。

### 2.2 签名点：只有一处

在 `NodeAgent.submit()` 中对**尚未签名**的消息签名。

- `submit` 是唯一的**发源**路径（限流、入队、登记重传都从这里开始）；
- `forward` 是转发路径，它用 `replace` 保留 `checksum`，因此**不会**、
  也**不应**重签（重签会顶着中继的身份，接收端会判 `BAD_AUTH`）；
- 对抗注入**绕过** `submit` 直达 `_on_rx`，因此注入的消息默认**不带**
  有效 MAC——这正是我们想要的：外部攻击者没有组密钥。

一处签名的好处是不会有「某个构造点忘了签」的漏洞。代价是 `submit` 必须
区分"发源"与"转发"，已由"checksum 是否为空"承担。

### 2.3 校验点：必须最先

`accept()` 的规则顺序原为「任期 → 会话 → 任务版本 → 去重 → 序列」。
认证必须插到**最前**：

**未经认证的消息，其所有字段都不可信**——包括 `leader_epoch`。若先比
任期，冒充者只要声称一个很大的 `leader_epoch` 就能让接收端接受它并
推进自己的任期视图，认证就形同虚设。

`BAD_AUTH` **必须与既有原因分开**：混用会让「被伪造」和「自己掉线」
在日志里长得一样，攻击不可观测——本项目已因同样的理由把
`SEQ_OUT_OF_WINDOW` 与 `STALE_SEQ` 分开过一次。

## 3. 默认关闭：向后兼容

`auth_enabled: bool = False`（默认），`auth_key: str = ""`。

与 `on_battery_empty="none"`、`energy_model="linear"` 同一模式：
新机制默认不改变既有行为，因此 **golden digest 逐位不变**，报告里已有
的数字无需复核。认证在场景配置里显式开启。

## 4. 对抗注入的分类：认证防什么、不防什么

认证改变了对抗日志里各攻击的含义，必须说清：

| 攻击 | 认证开启后 | 由谁挡下 |
|---|---|---|
| `stale_epoch` / `expired` / `forged_join`（外部伪造，无密钥） | 在认证处即被拒 | **认证** |
| `replay`（重放**抓到的真实**消息，MAC 有效） | 通过认证 | 序号窗口 + 去重（认证**不防重放**） |
| 内部成员伪造 | 通过认证 | **不防**（组密钥固有边界） |

因此 `Attack` 增加 `signed: bool = False`：置真表示「这条注入携带有效
MAC」（模拟抓包重放或内部人），用来分别验证两类防线。有了它，测试才能
证明认证**确实挡住了伪造**，而不只是「注入都失败了」。

## 5. 验收

1. 认证开启时，未签名的伪造消息判 `BAD_AUTH`，**且不污染**接收端的
   序号状态（后续真实消息仍被接受）——这是残差的正面复现。
2. 认证关闭时，行为与既有完全一致（digest 不变）。
3. 带有效 MAC 的重放仍由序号/去重挡下（认证不越俎代庖）。
4. `src` 被篡改而 MAC 不变的伪造必须失败（`src` 在覆盖范围内）。
5. `hop`/`ttl` 改变后 MAC 仍有效（多跳转发不被误杀）。
6. 签名为**确定性**函数（同一消息同一密钥恒得同一 MAC）。
7. 认证开启的完整场景可跑通，且正常节点的消息不被误拒。
8. 全套测试通过；golden digest 逐位不变（默认关闭）。
