# P2 规格：三处协议缺口修复

> 本规格由结果章节自己的「下一步」清单驱动（`docs/report/2026-10-04-results-chapter.html`
> 本章小结）：**中继布点优化、序号窗口校验、主节点故障切换**。
> 前两项来自实测缺口，第三项来自一次对抗式审查发现的 CRITICAL 缺陷。

## 0. 分类

**architectural**。三项都改动组件间的接口或引入新的状态机：

| 项 | 为什么是 architectural |
|---|---|
| 序号滑动窗口 | 改动 `DropReason` 封闭枚举（对外契约）、接收判定顺序、日志不变量 |
| 主节点故障切换 | 新增选举状态机，改动 `leader_epoch` 的语义（此前恒为 0）与任务归属 |
| 中继布点优化 | 改动世界初始化与路由可达性的耦合方式 |

因此先出本规格，再按切片实现，每片独立可测。

## 1. 切片 A：序号滑动窗口（优先级最高）

### 1.1 缺陷（已实测）

`skyfleet/protocol/version.py::accept()` 的末段：

```python
view.last_seq[key] = msg.seq          # 无上界
```

`last_seq` 只被推进、从不校验跃变幅度。冒充者发送**一个** `seq = 10^7`
的包即可把接收端的 `last_seq` 推到 10^7，此后所有真实节点的心跳
（`seq` 只有几十）全部满足 `msg.seq <= previous` → 判 `STALE_SEQ` →
被丢弃。**单封包拒绝服务**，且受害者无从区分「自己掉线」与「被攻击」。

结果章节已把该缺口如实写入（表 10），并声明「修复方向是把序号检查改为
滑动窗口」。本切片完成该修复。

### 1.2 设计

在 `accept()` 中把单调比较替换为窗口判定，**并且不让越窗包推进 `last_seq`**：

```
W = 窗口宽度（默认 64，见 §1.3）

previous = view.last_seq.get(key)
if previous is not None:
    if msg.seq <= previous:
        return STALE_SEQ                  # 回退或重放，窗口不动
    if msg.seq > previous + W:
        return SEQ_OUT_OF_WINDOW          # 跃变过大，窗口**不动** ← 关键
view.last_seq[key] = msg.seq
```

**键不变**：仍是 `(src, msg_type, leader_epoch, mission_version)`。
理由已写在代码注释里——心跳与遥测的序号互不排序，把 `msg_type`
排除在键外会让一条乱序遥测把随后的心跳误判为过期。

**关键设计点**：拒绝越窗包时**不推进窗口**。否则冒充者只要连发
`last_seq + W` 就能把窗口一步步推到任意远处，DoS 依旧成立。

### 1.3 实现中发现的设计更正：发送端必须**分流计数**（原规格漏了）

原规格以为「窗口只要够宽就行」，实测推翻了这个想法。

原实现里**每个节点只有一个全局发送计数器**（`agent.py` 的 `self._seq`），
而接收端按 `(src, msg_type)` 校验。于是任一 `(src, msg_type)` 子序列都
会跳过其他所有类型，**合法跳跃无界**。实测基线场景：

| | 中位数 | p99.9 | 最大 |
|---|---|---|---|
| 全局计数（原） | 2 | 439 | **969**（`L` 的 ACK 流） |
| 分流计数（改后） | 1 | 7 | **12** |

在全局计数下，窗口上界**在本质上无界**——W 取多大都只是碰运气，
取 969 以上等于没有上界，取 64 则会让 57 条**合法**消息在干净基线里
被误判为攻击（实测：golden digest 因此变化）。

**因此本切片包含第二处修改**：`next_seq()` 改为按 `msg_type` 分别计数
（`self._seq: dict[str, int]`）。分流之后 W = 64 相对实测最大值有
**5.3 倍余裕**，上界才真正有意义。

这也解释了为什么该缺陷此前从未被发现：全局计数是**单调**的，
所以在原来的「只做单调比较」下，子序列同样单调，永远不误判。
是**加上上界**这个动作，才把底下的问题翻了出来。

### 1.4 窗口宽度的取值依据

`W` 必须大于「该流自身丢包能拉开的距离」。分流计数后，该距离
受**单条流的在途与丢失包数**限制，实测最大 12（见上表）。
取 `W = 64`：相对实测最大值 5.3 倍余裕，又远小于冒充者的跃变尺度
（10^7 量级）。`W` 作为 `accept()` 的参数注入（默认
`DEFAULT_SEQ_WINDOW = 64`），便于测试与后续标定。

### 1.4b 已知残差：先到的冒充者防不住 → **P4 已关闭**

> **状态（2026-10-09）**：本残差已由 P4 消息认证关闭，见
> `2026-10-09-p4-message-authentication-spec.md`。`auth_enabled=True`
> 时冒充者在认证处即被拒（`BAD_AUTH`），接收端的序号状态不被污染。
> 默认仍为关闭，故本节描述的默认行为**逐字不变**。
> 验证：`tests/unit/test_auth.py::TestFirstArrivingSpoofer`（两侧对照）
> 与 `tests/integration/test_message_authentication.py`。


无认证时，若接收端**从未见过**这条流，就没有基准可判断 10^7 是否离谱，
它会被当作锚点，此后真实心跳确实被误判。

这不是实现缺陷，而是「无认证的序号窗口」的本质边界——消息结构里的
`checksum` 至今仍是 P0 占位。本残差已由
`test_a_first_arriving_spoofer_is_a_known_residual_gap` 固定下来，
避免有人误以为滑动窗口已经等于安全。要真正挡住它需要认证（签名/MAC），
属独立课题。

### 1.4 测试（TDD，先红后绿）

1. **单封包 DoS 必被挡住**（核心回归）：注入 `seq = 10^7`，断言返回
   `SEQ_OUT_OF_WINDOW`；随后注入 `seq = 1..5` 的真实心跳，断言**全部被接受**
   ——这一条直接复现并钉死原缺口。
2. **越窗包不推进窗口**：注入 `seq = 10^7` 之后再注入 `seq = W + 2`，
   仍须被判越窗（若窗口被推进，这一包会被误接受）。
3. **窗口内乱序仍被接受**：`previous = 10`，注入 `seq = 11..10+W` 逐个接受；
   断言实测最大可接受跃变恰为 `W`。
4. **回退仍判 STALE_SEQ**：`seq <= previous` 走原分支，窗口不动。
5. **封闭枚举对账**：`SEQ_OUT_OF_WINDOW` 必须同时进入 `DropReason` 与
   `EventKind` 两侧，且 `tests/integration/test_log_invariants.py` 的
   `CAUSE_SETS` 对账通过（该测试此前抓出过 `STALE_SEQ` 不在枚举内的同类问题）。
6. **对抗注入的端到端**：`AdversaryInjector` 的序号攻击在真实日志里
   体现为 `SEQ_OUT_OF_WINDOW`（而不是 `STALE_SEQ`），且任务的完成率
   **不低于**无攻击基线（DoS 已被挡住）。

### 1.5 风险

- **误伤合法跃变**：若未来引入「批量重编号」或「会话内序号重置」，
  合法跃变会超窗。当前实现没有这类机制，故不预留；若将来引入，
  应当重置 `last_seq` 而不是放宽 `W`（放宽 `W` 会同时放宽攻击面）。
- `leader_epoch` 已在键内，因此重新选主（切片 B）后窗口自动分开，
  不会把新任期的小序号误判为回退。

## 2. 切片 B：主节点故障切换

### 2.1 缺陷（已实测并修复一半）

对抗式审查发现：坠机的主节点仍在指挥。已修的部分是**让死掉的主节点
停止写事件**（`_on_leader_check` 增加 `if not agent.alive: return`），
但**没有任何节点接管**。实测后果：主节点在 t=485.1 电量耗尽后，
集群到仿真结束（900 s）**再没有任何任务编排**——剩余 400 多秒里，
未完成任务既完不成也不会被判失败。

结果章节与设计文件均已如实声明「本模拟器没有主节点故障切换」。
本切片实现它。

### 2.2 设计

复用既有的 `leader_epoch`——它当前被初始化为 0、**从不递增**，
导致 `STALE_EPOCH` 分支是死代码（P1 文档已记录）。

**选举规则（最小可用）**：

- 触发：任一节点在 `T_ELECT`（默认 `3 × heartbeat_period`）内未收到
  主节点心跳，且自己**不在** `grounded`/`busy`（中继不参选）集合内。
- 候选人按 `node_id` **字典序**最小者当选（确定性，不引入新随机流）。
- 当选者 `leader_epoch += 1`，发出 `LEADER_ANNOUNCE`，开始承担编排职责。
- 其余节点收到更高 `leader_epoch` 后更新本地视图；
  `accept()` 的任期检查（`STALE_EPOCH`）此时**才真正生效**，
  旧主节点若复活（`revive`）也无法再用旧任期下令。

**不改动的东西**：不引入 Raft/Paxos。本仿真的目标是**可观测的协议行为**，
不是分布式共识的正确性证明；规则必须简单到能在报告里用一段话说清，
并且能解释每一条新事件。若要更强保证，应先有明确的论文级需求。

### 2.3 测试

1. **主节点死后有节点接管**：杀死主节点，断言存在 `LEADER_ANNOUNCE`，
   且新主节点的 `leader_epoch` 严格大于旧的。
2. **接管后任务继续被编排**：断言主节点死亡时刻之后仍有 `TASK_ASSIGN`
   事件（当前为 0 —— 这一条直接复现原缺陷）。
3. **确定性**：同一场景重复运行，当选者相同、`LEADER_ANNOUNCE` 时刻相同。
4. **中继不参选**：断言当选者不在 `relay_ids` 内。
5. **旧主节点复活不能复辟**：`revive` 旧主节点，断言其消息因
   `STALE_EPOCH` 被拒。
6. **不退化**：无故障场景下**不产生**任何 `LEADER_ANNOUNCE`
   （golden digest 必须逐位不变）。

### 2.4 风险

- **golden digest**：无故障路径必须完全不受影响。新增事件只在故障路径产生。
- **选举风暴**：两个节点同时自认当选。用字典序 + 任期号打破，
  并加测试固定「同一时刻只有一个节点宣告」。
- **与切片的交互**：选举后 `leader_epoch` 变化，序号窗口键随之改变，
  切片 A 的窗口不会误伤新任期（已列入 §1.5）。

## 3. 切片 C：中继布点优化

### 3.1 现状

中继按固定环布局：内环 `radius = 0.18 × area`、高度 `z = high`（见
`skyfleet/sim/engine.py`）。P1 的结论是「中继门限在两轮扫参中均无可测影响，
**根因是中继布点而非门限**」——门限调不动，是因为布点让中继要么全都够得着、
要么全都够不着。

### 3.2 设计

**本切片只做「可比较的布点」这一件事**，不做优化算法。理由：在没有
可比较的布点之前，任何「优化」都不可验证——这正是 P1 那一轮扫参失败的原因。

提供三种布点，作为 `config.relay_layout` 的取值：

| 值 | 布点 | 用途 |
|---|---|---|
| `ring`（默认） | 现状：内环 + 高高度 | 向后兼容，digest 不变 |
| `grid` | 按 `ceil(sqrt(n))` 均布于任务域 | 消除「环」带来的对称偏置 |
| `farthest` | 贪心：每次选距已选点集最远的候选位置 | 作为**上界参考**，不当作实用方案 |

### 3.3 测试

1. **`ring` 逐位不变**：默认布点下 golden digest 不变。
2. **布点确实不同**：三种布点产生不同的中继坐标。
3. **`farthest` 的可达性上界**：断言其平均链路质量不低于 `ring`
   ——若不然，说明「最远布点」的直觉是错的，这个结论本身要写进报告。
4. **可比较性**：同一协议参数下，三种布点的完成率差异用切片 A/B 之外的
   独立扫参报告，且**必须跨多个 `env_seed`**（否则重蹈 §11 的覆辙）。

### 3.4 风险

- **对称性**：`ring` 布点有旋转对称性，可能让某些协议效应被对称性掩盖。
  `grid` 切片正是为了检验这一点。
- **不要把「优化」当结论**：若三种布点差异不显著，应当如实报告，
  而不是换一个指标继续找显著性（多次比较问题，见分析文档 §11.4）。

## 4. 实施顺序与验收

| 顺序 | 切片 | 验收 |
|---|---|---|
| 1 | A 序号滑动窗口 | ✅ 单封包 DoS 被挡住；`DropReason` 13 → 14；发送端序号改为分流计数；日志不变量对账通过 |
| 2 | B 主节点故障切换 | ✅ 主节点死后有接管、任务继续编排（完成率 0.000 → 0.85）；无故障路径 digest 不变 |
| 3 | C 中继布点 | ✅ 三种布点可比较（转发量相差 13 倍）；`ring` digest 不变；跨 `env_seed` 报告见 `docs/analysis/2026-10-07-relay-layout-comparability.md` |

每片都必须：先写红测试 → 最小实现 → 全绿 → 更新受影响的文档 →
`git commit`（一片一提交）。

**共同验收**：`python3 -m unittest discover -s tests -t .` 全绿；
`tests/determinism/test_golden_digest.py` 中线性路径的摘要**逐位不变**
（物理模型与故障路径的改动不得触碰它）。

## 5. 明确不做

- **不引入分布式共识**（理由见 §2.2）。
- **不修涡环状态建模**（P1 已知限制，与协议无关）。
- **不做中继布点的自动优化**（理由见 §3.2）。
- **不改 `safety_decision` 只记录不执行**的现状——它是已知的未接线缺口，
  但与这三项无关，混进来会让每片的验收边界模糊。
